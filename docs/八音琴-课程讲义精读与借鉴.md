## 二、逐课要点（每课 3~5 条）

### 第1课《从想法到开工：AI 硬件起步指南》

1. **两套 AI 角色**：把 AI 做进产品（提升产品能力）与 用 AI 来做产品（加速研发）是两类问题；MCP/Skill 让 AI 能真正读资料、改工程、构建烧录。
2. **硬件闭环必须回到真机**：编译/测试通过 ≠ 功能完成；"程序通过 + 真机给出符合要求的反馈"才算完成（课中"喇叭没声音"案例）。
3. **人做判断，AI 加速开发**：人决定值不值得做、确认方案、验收真机；AI 负责资料/工程/代码/构建。2026 路线 = "先跑通，再理解，最后改造，现学现用"。
4. **需求为何必须做成硬件**：五个现实限制（操作成本、注意力占用、现场反馈、物理动作、现场条件）；三问（使用者价值 / 拥有者负担 / 未使用者影响）；反对"为了像 AI 硬件而加设备"。
5. **开工四环节**：整理硬件资源（板型/原理图/PCB 正反面/GPIO 表）→ 让 AI 判断并搭环境 → 对齐项目上下文（**先让 Agent 复述、人纠正**）→ 选工程起点做最小开发。项目文件夹固定三件：`hardware/`、`firmware/`、`README.md`。

### 第2课《跑通第一条 AI 硬件开发链路》

1. **核心判断标准**：Vibe Coding 不是把判断交给 AI，而是**让 AI 缩短想法到真机验证的距离**。
2. **四个 AI 开发入口（Skill）**：`easy-input-maker`（开发对象）、`project-flow-cy`（目标/边界/交接）、`easyinput-board-cy`（硬件真相源）、`esp-idf-cy`（环境/构建/识别/烧录/串口）。
3. **四阶段 12 节点**：读懂与基线(01-03，只读不改、先证原项目正常) → 协议与实现(04-06，核对已冻结协议、接入八个键) → 通道与构建(07-09) → 写入与验证(10-12，先审 diff 再烧录再按真机验证)。
4. **四种结果不能混**：电脑侧测试通过 ≠ 构建成功 ≠ 已写入板子 ≠ 真机功能成功；每步只证明它自己那步。
5. **Host Action v1 机制点**：UUID 是动作专属识别码（非应用编号）；固件**不保存**应用名/路径；按下发一次、松开不发；有线/BLE 同内容且**双连接不双发**；消息格式已约定，**不能临时换写法**。真机有**七项检查表**。

### 第3课《AI 键盘哄我上工 & EasyInput 上的实时鼓机》

1. **克制**："没有因为它有八颗键，就制造八个需求"；只改了一颗本来闲置的 S3——**先让它能跑，再用自己的方式改一处**。
2. **软件层优先**：很多"定制硬件"根本不需刷固件，把已有软件动作放到手指够得到的地方即可（App 的"固定文字/快捷键/打开应用"三种动作）。
3. **明确反馈是刚需**：整理完 57 个文件后第一反应是"至少给我一个 log 吧"→ 补上结果弹窗（**报总数/分类/耗时**）；并让灯"用起来"（状态提示）。
4. **鼓机方法论**：**发声与走拍始终在板端，电脑不得当节拍器**；节拍用 **I2S 音频采样游标**做主时钟（不用 delay）；分阶段 P0→P1→P2→P3，**完成当前阶段验收再进下一阶段，别跳步**。
5. **协议/同步实践**：Newline JSON + `hello.v=2`/`state` 握手进入 `synced`；Pattern 用 `rev`（revision）做主机↔设备同步；音频线程约束（不动态分配、不等待锁、不直接写 WS2812）。

### 第4课《一键启动我的内容创作工作台》

1. **五层结构**：输入 → 触发(按键/编码器) → 路由(选 Agent) → 执行(Skill+模型) → 资产(文档/表格/云盘/本地文件)。价值：**哪层不好用就换哪层**，Agent 变了按键仍能用。
2. **场景筛选三问**：是否经常出现？流程是否相对稳定？手工启动是否麻烦？——只有高频、稳定、启动麻烦的任务才值得占用物理按键。
3. **Skill 保存"做事习惯"**：受众、组织、语气、输出物、验收标准、缺料标记、**何时停下来等确认**。按键里放"稳定规则"，当次主题/素材用语音或文字补充。
4. **按键分工两法**：按内容类型分配 或 按流程步骤分配；至少三个键，逐一交代键位/场景/配置方式。
5. **迭代观**：记录"卡点=现象+处理"，Skill 第一次不必完美；连续使用一周、多次运行，留下可观察痕迹（别维护低频键）。

### 第5课《AI 时代不可被取代的技能：软硬件结合的英语学习》

1. **效率 = 更短、更稳定的路径**，不是手速；鼠标是"请求"（找位置/移动/点击/等待），键盘/命令是"直接发出命令"；**只优化高频、规则稳定、可预测、会打断注意力的动作**。
2. **核心产品公式**：真实痛点 + 最小交互循环（选择→确认→反馈→下一题）+ 少量实体指令 + 立即反馈；硬件 = "高频意图的实体入口"，不替代电脑。
3. **通用键位原则（关键）**："不要让学习者操作软件，让他操作英语"——**不要把八个键焊死成菜单式分配**；让多数键**在任何模式下含义不变**（上一题/下一题/播放/提交/查看），**只留 S3/S4 两个位置给"当前模式特有动作"**。
4. **把"找答案"和"移动"留在同一部件**：转旋钮=循环候选，按旋钮=确认并跳到下一处，只有"提交"这种低频动作交给独立按键；手不用来回切换。
5. **五颗 LED = 把网页视觉反馈搬到桌面**：闲置全暗 / 播放呼吸灯 / 答对全绿闪 / 答错全红闪 / 结果用"实心灯数=分数"点亮 / 待机用亮灯数提示剩余 Weak Point。

### 第6课《给世界换一种颜色：StyleCam 风格调色盘》

1. **用户旅程先行**：先画**六张草图**（空工作台/放素材/选风格/生成等待/结果放大/结果收起），每张只写**当前目标、允许动作、结束条件**；反对"主页变平铺控制台"。
2. **区分易混概念，避免误触发**："风格"决定生成对象/材料；"创意强度"是提示词改造幅度；"创意显示"只是对已有图做实时呈现——**调显示不会重新生成，只有明确"生成"动作才提交任务**，让用户敢放心旋转探索。
3. **软硬件分工**：软件管理内容与状态；硬件提供顺手、可触达的高频输入（转/按/点三类手势）。
4. **改配置的顺序与善后**：先**保留原配置**（截图留档），一次只改一项；同步失败按"一项一项变更"定位（如睡眠项与固件不兼容）。**按键功能（做什么）与硬件键值（网页如何认出）是两件事**，分开配。
5. **五分钟校准实验**：慢转左右各十格看方向与"一格跳多项"、短按是否只执行一次、切到别的应用是否仍触发；排查要**先区分固件发了多个事件还是网页把 keydown/keyup 都当执行**，别用长延迟硬压。

### 第7课《一把键盘，远程开发，Codex 任务电台》

1. **十张基础概念卡**：网络分层、配网、**Flash 分区与 NVS**、声音数字化、认证加密、Generation 代际、FIFO 排队、什么算"任务完成"、"真正听完才算听过"、后台服务。**"三个角色、两条链路"（说进去/听回来）** 的全景架构。
2. **分区与写入范围（重点）**：16MB Flash → bootloader `0x0`、分区表 `0x8000`、NVS `0x9000`、PHY `0xF000`、应用 `0x10000`、独立音效区 `0x310000`/`0x3A0000`。**烧录只写三段（引导/分区表/应用），不擦 NVS**；**整片擦除（erase_flash）会清空 NVS 与音效区**，不要额外执行。换分区布局要另行评估数据迁移。
3. **烧录先对指纹**：先记三个镜像 SHA 再烧，"报成功不等于烧了你以为的镜像"；先启带 `usb_reset` 的等待命令再断电上电抓窗口；端口必须用实际唯一端口。
4. **最小验收表 C4（7 条可填）**：①按住说话松手→进队列 ②运行中第5灯黄 ③完成音频发布→第1灯亮 ④按S5→播完灯灭 ⑤播放中按住PTT→立刻让位、灯不灭 ⑥同槽连说两条→严格按序 ⑦旋钮停≥1s后断电重启→档位一致。**逐条填实测+版本+失败现象，不因为代码已实现就代填通过**。
5. **排错方法**：**先分层再提问**（测试通过/Host发了包/键盘收包/扬声器响/灯灭，各只证明自己那层）；排错 prompt 模板（现象/期望/已确认/日志 + **"先告诉我最可能 3 个原因和验证方法，先不要给修复代码"**）；**先诊断后动刀**；怀疑 AI 的三条信号（破坏不可破坏语义、"测试通过即功能正常"、一次改五个文件修一个现象）。

### 第8课《结营课：用同一套方法，开始下一个 AI 硬件项目》（老师课件待补充，正文为学员整理）

1. **方法循环**：资料先行 → AI 协同 → 真机验证 → 软硬件迭代；最常被跳过的是第一步（不给资料 → AI 靠猜 → 任务跑很久却像没动）。**硬件不稀缺，软硬件协同才稀缺**。
2. **真相源三件套**：原理图（连接关系唯一依据）、GPIO 表、BOM 表、芯片/屏幕手册（**PDF 转 Markdown** 喂 AI）；并给资料**标日期**。四条原则：资料先行 / 从根源解决不打补丁 / 资料适配 / 上下文同频。
3. **交互设计 8×8=64（最"产品"的一节）**：硬件形态固定却"8 键不够用"→ 8 键 × 8 应用上下文。**快捷键到应用相当于两级菜单，会变复杂**；解法是**交互场景**（按住滚轮呼出"应用中心"列出可切换应用）而不是堆键帽。设计原则原文：**"能用一个场景解决的，就不要用一个两级菜单。反馈要明确——视觉和听觉都要有。"**
4. **两条必处理的细节**：**兜底逻辑**（没有输入框/未聚焦时，不要只弹错误，**自动把选中文字复制到剪贴板**，别让"我说的话白说"）；**保留默认按键退路**（否则切到别的应用就回不来）。
5. **demo→量产四条前置设计**：优先模组慎用裸芯片 / **提前预留 OTA**（开发初期就设计进去，否则只能返厂修）/ 硬件固定后用固件·软件迭代 / **把配网体验当回事**（退货核心诱因）。附"打板红线"：自行设计 PCB 必须找有经验的硬件工程师复核。

## 三、对「八音琴」项目的可借鉴 / 应改进之处

> 「八音琴」现状基线（据 `八音琴-需求与决策记录.md`、`八音琴-变更与会话记录.md`）：ESP32-S3 + 8 键 + EC11 旋钮 + 5 颗 WS2812(D1~D5) + 独立 PWM 状态灯 + 喇叭；固件为主（现场合成发声），网页 `web/index.html` 经 host_link v2(换行 JSON) 双向通信；已预留 OTA（分区表里本工程归属槽为 `ota_3`，**实际烧录/运行在 `ota_0`@`0x20000`**）；曲库 5 槽，`rec` 分区持久化；语音由 `rec` 分区播放。

### 3.1 交互设计（作业/课件反复强调：避免两级菜单、场景化、明确反馈）

- **通用键位优先，上下文键越少越好**（L5 核心）。建议范式："**多数键在任何场景含义不变**，只留极少数键随场景变义"。对照八音琴现状：主目录 `S1~S4` 是"入口"、试听 `S1~S5` 是"选曲"、自弹 `S1~S8` 是"弹音"——**同一排键在每个场景含义都不同**，正是课里点名的"菜单式分配/两级菜单"反例。
- **场景化反馈要"视觉 + 听觉"双通道且明确**（L8/L3）。八音琴已有语音提示与灯，建议每条关键动作都成对：如"保存第 N 首"→**语音报数 + 对应 D_N 亮一下**；避免只做其一。
- **兜底与退路**（L8）。八音琴已有"空槽播报暂无记录""游戏失败丢弃不落槽""长按回主目录"，方向正确；建议把"**回主目录**"确认为任意场景的通用逃生键（与 L5 的"长按≥1.5s 回 Dashboard"、L8 的"保留默认按键退路"同源）。
- **把高频动作放同一部件**（L5）。八音琴"旋钮=音量（所有场景统一）"符合该原则；可借鉴"转=浏览候选、按=确认"的分工，让旋钮承担"调音量"之外的少量"选择/确认"。

### 3.2 软硬件协同

- **发声/走拍留在板端**（L3 硬规则）。八音琴现场合成 + I2S 32kHz 已符合；**录制回放建议节拍以 I2S 采样游标为时间基**（而非 `vTaskDelay`/网页计时器），避免长跑漂移。
- **明确板端与网页分工**（L4/L5/L7）：硬件=顺手的高频输入与实时发声，网页=内容/状态/编辑。八音琴协议分工与之一致；建议网页侧只做"看见与修改"，**不生成板端拍点**。
- **主机↔设备握手与版本**（L3）。建议在 host_link v2 上补 `hello`/`state` 式握手（识别设备身份与协议版本）与**曲库 revision**，把"已同步"做成明确状态，减少"看起来连上了但没同步"。
- **音频线程约束**（L3）：音频渲染线程不动态分配、不等待 UI/USB 锁、不直接写 WS2812。

### 3.3 ESP-IDF 工程实践（分区 / OTA / NVS / 驱动）

- **写入范围与"不动 NVS"**（L7）：八音琴铁律"不动分区表、不擦 NVS、不整片擦除"与课里易错点完全一致，保持。烧录时只写必要镜像（引导/分区表/应用），并注意 `tools/voice_prompts/voice_prompts.vpmt` 需**单独写到 `rec` 分区 offset `0x9D8000`**。
- **OTA 必须提前预留**（L8）：八音琴已在分区表里预留归属槽 `ota_3`（1MB，本工程 app 962,880 B，放进它也余 ≈85.7 KB）——保持；注意**本次实际烧录落在 `ota_0`@`0x20000`**（`idf.py flash` 的口径）。建议补一条"**OTA 回滚/断电中断/版本迁移**"的真机验证项（L7 卡3 提到换分区布局要评估数据迁移）。
- **指纹优先**（L7）：烧录/写语音前先记镜像 SHA，"报成功不等于烧了这份镜像"；`Hash of data verified` 只代表写入校验通过，仍需验重启枚举与真机现象。
- **配网（如未来加 Wi-Fi）**：密码只从标准输入传给命令、**不写进命令行参数**（会留在 shell 历史）；配网体验直接影响退货率（L8）。

### 3.4 测试与验收方法

- **四种结果不能混**（L2）：八音琴"先测后烧"正是此意——电脑侧测试 ≠ 构建 ≠ 烧录 ≠ 真机。建议汇报时把四态分开陈述，禁止用"测试全绿"代表"功能完成"。
- **分阶段验收、别跳步**（L3）。八音琴阶段 ①能弹 ②会记会放 ③会教 ④上网页——建议给每阶段写**可勾选的验收清单**（如 L3 的 P0~P3、L7 的 C4 七条），完成当前阶段验收再进下一阶段。
- **真机七项/最小验收表**（L2/L7）：建议为八音琴建一张"真机验收表"（例：8 键逐个出正确音高与颜色 / 旋钮音量方向正确 / 记谱保存与回放 / 长按回主目录 / 空槽兜底 / 断电重启后曲库仍在 / 语音提示可听）。
- **排错先分层 + 先诊断后动刀**（L7）：按"按键→固件事件→音频→扬声器→灯"分层定位，向 AI 要"最可能的原因 + 验证方法，先别给修复代码"。

### 3.5 文档与资料先行

- **真相源三件套 + 标日期 + 转 Markdown**（L8）：八音琴已有 `easyinput-board-cy` 硬件真相源与"硬件红线"表，建议把 GPIO 表/分区布局/协议文档集中进项目上下文，并给资料**标日期**，便于"这是哪一版"。
- **让 Agent 先复述再动手**（L1）：开工时先让编程 Agent 用自己的话复述板型/引脚/工程现状，人纠正后再改。
- **交付文档的可读性**（L8 六问 + L3 评分）：文档要让"小白也能看懂"；**"做了但没写 = 没分"**，过程要能辨认出"你自己的步骤"。

### 3.6 ⚠️ 与本项目已冻结设计冲突 / 需用户拍板（不擅自改设计）

| # | 冲突点 | 冻结设计（现） | 课件主张 | 处置 |
|---|---|---|---|---|
| C1 | **键位语义模型** | 主目录 `S1~S4` 进 4 个子目录、各场景键义不同（**两级菜单式**，见 `需求与决策记录` §1/§2） | L5："不要让学习者操作软件，让他操作英语"，多数键跨模式含义不变，仅少数键随场景变义；L8："能用一个场景解决的，就不要用一个两级菜单" | **需用户拍板**：考虑改为"通用键位 + 极少数上下文键"，或为"场景切换"提供更短的可见入口（如按住旋钮呼出"模式中心"，参考 L8 应用中心） |
| C2 | **"回主目录"长按时长** | 长按旋钮 **≥5 秒** = 回主目录（任意场景通用） | L5 用 **≥1.5 秒** 回 Dashboard；L8 用"按住滚轮呼出应用中心" | **需用户拍板**：5s 偏长、易被当作"没反应"；可考虑缩短或加中途反馈（如长按进度灯/提示音），但这会改冻结决策 |

## 四、可复用的技术做法 / 模板摘录（可执行要点）

### 4.1 ESP-IDF / 烧录 / 分区（来自 L7）

- **分区布局参考（16MB，EasyInput 同类板）**：`bootloader 0x0`｜`分区表 0x8000`｜`NVS 0x9000`｜`PHY 0xF000`｜`应用 0x10000`｜独立音效区 `0x310000 / 0x3A0000`。（⚠️ 这是讲义给的**旧版 A 族布局**；本工程已改用 **6 槽表**，app 实际写 **`0x20000`（`ota_0`）**，见 `firmware/partitions.csv` 与 `firmware/build/flash_args`。）
- **只写三段的 esptool 模板**（八音琴按自己实际镜像/SHA/分区调整，**不要照抄**）：
  ```bash
  python -m esptool --chip esp32s3 -p "$PORT" -b 460800 \
    --before usb_reset --after hard_reset --connect-attempts 0 write_flash \
    --flash_mode dio --flash_freq 80m --flash_size <实际容量> \
    0x0    build/bootloader/bootloader.bin \
    0x8000 build/partition_table/partition-table.bin \
    0x10000 build/<app>.bin
  ```
  要点：先核对**三镜像 SHA**；用**实际唯一端口**（不通配符）；先启动带 `usb_reset` 的等待命令，再让操作者断电上电抓窗口；`Hash of data verified` ≠ 真机可用。
- **禁忌**：`erase_flash`（整片擦除）会清空 NVS 与音效区——**不要额外执行**；换分区布局要评估数据迁移。

### 4.2 最小验收表模板（来自 L7 C4，可套用到八音琴）

| # | 动作 | 期望 | 实测结果 | 版本 | 失败现象 |
|---|---|---|---|---|---|
| 1 | （例）按住 S8 记谱→松手保存 | 落槽并语音报数 | | | |
| 2 | （例）断电重启 | 曲库仍在 | | | |
| 3 | （例）旋钮音量 | 方向正确、松手后一致 | | | |
| … | | | | | |

> 规则：**逐条填实测 + 版本 + 失败现象**；不因为"代码已实现"就代填通过。

### 4.3 排错 prompt 模板（来自 L7 D2）

```text
【现象】<一句话描述现象，如"按 S8 保存后灯亮但无声">
【期望】<期望结果>
【已确认】<已排除的层：如宿主测试通过、同一端口、昨天还正常>
【日志】<粘贴相关日志片段，删掉隐私内容>
请先告诉我最可能的 3 个原因和各自的验证方法，先不要给修复代码。
```
> 关键：**先诊断，后动刀**；分层表——测试通过 / 主机说发了 / 设备收到 / 扬声器响 / 灯灭，各只证明自己那层。

### 4.4 "改一处" 与"连续使用"记录模板（来自 L3/L4）

- **改一处三要素**：改哪一层（固件/网页/配置/按键动作/提示语/音频）+ 改前是什么 + 改后是什么（**具体到别人能复现**）；动机与自身习惯/需求相关；效果验证可辨认。
- **卡点表**：`卡点环节 | 看到的现象 | 初步原因 | 做了什么调整 | 调整后结果/待验证`。
- **连续使用表**：`日期/次数 | 使用的真实选题 | 用了哪些按键 | 哪里变顺/仍不顺 | 本次修改`。

### 4.5 主机↔设备协议实践（来自 L3）

- Newline JSON + 版本字段（`hello.v`）；`hello` + `state` 两条都有效才进入 `synced`。
- 编辑对象用 **revision**（`rev`）标识：网页提交带已知 rev → 设备接受后递增并回确认；冲突时以设备数据更新网页草稿。
- 静默期保护：录音/对局期间锁定会打断流程的按键（如播放/A/B 切换）。

## 五. 一句话结论

8 课讲义对八音琴最有价值的并非某个具体功能，而是**一套方法**：资料先行、软硬件各司其职、真机验收逐条可查、分阶段别跳步。其中**最需用户拍板的**是：八音琴现有的"主目录→子目录 + 各场景键义全变"是否属于课件明确反对的**两级菜单式交互**（见 §3.6 C1/C2）。
